### 2.2 システムアーキテクチャ (ADR) への準拠状況
- **ADR-1: サーバーサイド永続化（`UserProperties`）の主ストレージ採用**:
  - **準拠**: iframe サンドボックスに依存しない恒久的なストレージとして正しく機能。起動通信 `getAppConfig` に統合することで追加ラウンドトリップ（0 RTT）を実現。
- **ADR-2: 多層防御型フォールバックチェーン（URL > UserProperties > localStorage > Default）の採用**:
  - **準拠**: `resolveInitialFolderId` 関数により厳格に優先順位が解決され、ディープリンクと通常作業再開の両立を達成。
- **ADR-3: クライアントストレージの防御的カプセル化（`SafeStorage`）**:
  - **準拠**: `index.html` 内の全 `localStorage` アクセスが `SafeStorage`（`get`, `set`, `remove`）経由に完全置換され、例外スロー環境でもクラッシュしないことを確認。
- **ADR-4: フォルダ変更時の楽観的UI更新と非同期・非ブロッキング永続化**:
  - **準拠**: `applyFolder` において保存と一覧取得が並行実行され、軽快なUXを維持。

## 3. 品質・技術的負債監査

### 3.1 コード品質 / 保守性 / シンプルさ
- **コードの明瞭性**:
  - `コード.js`（338行）、`index.html`（893行）ともに適切な JSDoc コメントが付与され、処理の意図と責務が明瞭です。
  - 不要な外部ライブラリを追加せず、標準の JavaScript (ES6+ / V8 ランタイム) および Tailwind CSS で完結しており、軽量かつ高凝集に保たれています。
- **パイプ記号・構文規約**:
  - 半角パイプ記号（`|`, `||`）が正しく記述されており、LaTeX 特殊文字の混入や構文エラー、未実装プレースホルダー（TODO）は皆無です。

### 3.2 結合度と凝集度
- **疎結合性**:
  - サーバー側 API（`getAppConfig`, `saveLastFolderId`, `clearLastFolderId`, `getHtmlFileList`）は直交性が高く、クライアント側と REST/RPC 的な明確なインターフェースで分離されています。
  - クライアント側ではストレージ層（`SafeStorage`）、判定ロジック（`resolveInitialFolderId`）、状態制御（`applyFolder`, `executeSearch`）、プレゼンテーション層が明確に役割分担されています。

### 3.3 エラーハンドリング・セキュリティ
- **セキュリティ (XSS・インジェクション耐性)**:
  - `renderFileList` 内で `escapeHtml` を徹底しており、ファイル名による DOM-based XSS は遮断されています。
  - サーバーサイド `doGet(e)` からクライアントへの値注入（`SERVER_URL_FOLDER_ID`）は、サーバー側で厳格な英数字バリデーション（`/^[a-zA-Z0-9_-]+$/`）を通過した値のみが展開されるため、インラインスクリプト破壊やコードインジェクションのリスクはありません。
- **例外遮断 (Graceful Degradation)**:
  - ストレージ制限、ネットワーク切断、フォルダのゴミ箱入り、権限剥奪の各レイヤーにおいて、例外が漏れて画面がホワイトアウトすることなく、ユーザーへの適切な通知と安全なフォールバックが行われます。

### 3.4 テスト網羅性・適切性
- **テスト自動化の充実度**:
  - `tests/run_tests.js`: 構文チェック、サーバー単体、クライアント単体、結合、リグレッション、バグ再発防止を含む計31件が実装され、全件合格。
  - `tests/adversarial_tests.js`: セキュリティ、入力検証、自己修復、並行性、後方互換性に関する計11件の敵対的テストが実装され、全件合格。
  - モック環境（GAS V8, PropertiesService, HtmlService, DriveApp, localStorage）が的確に構成されており、リグレッション防止体制が確立されています。

### 3.5 長期的運用リスク・技術的負債
- **運用リスク**:
  - 極めて低リスクです。GAS の標準クォータ（1プロパティ 9KB、総容量 500KB）に対して、保存するデータは 33〜44 文字（数十バイト）のフォルダIDのみであるため、容量枯渇の懸念はありません。
- **技術的負債**:
  - 現状で解消すべき緊急の技術的負債は認められません。

### [改善提案 / Suggestion]
※以下の項目は現行の動作に影響を与えるものではなく、リリース後の継続的な改善（保守性・防御性の向上）に向けた推奨事項です。

#### 1. フォルダID入力値に対する最大長制限の導入
- **指摘内容**:
  - `sanitizeFolderId_` は英数字・ハイフン・アンダースコアの文字種チェックを実施していますが、文字列長のバリデーション上限（例: 128文字以内）を明示していません。
- **証拠**:
  - `コード.js` 41行目: `if (!/^[a-zA-Z0-9_-]+$/.test(cleaned))`
- **影響**:
  - Google Drive の正規フォルダIDは約33〜44文字です。悪意のあるユーザーが数千文字の英数字を入力した場合でも、正規表現チェック自体は通過し、`PropertiesService` の 9KB 制限境界に到達します（try-catch でエラー捕捉されるためシステム停止には至りません）。
- **推奨対応**:
  - 将来的な防御強化として、正規表現を `/^[a-zA-Z0-9_-]{1,128}$/` 等に改修し、極端な長大入力に対する早期バリデーションを設けることを推奨します。

#### 2. エラー判定の「文字列部分一致」から「エラーコード」への移行
- **指摘内容**:
  - `index.html` の `executeSearch` における自己修復トリガー判定が、サーバー側から返却される日本語エラーメッセージの部分一致（`includes('指定されたフォルダ')` 等）に依存しています。
- **証拠**:
  - `index.html` 578-585行目:
    ```javascript
    if (response.error && (
      response.error.includes('指定されたフォルダ') ||
      response.error.includes('ゴミ箱') ||
      response.error.includes('無効なフォルダID形式') || ...
    ))
    ```
- **影響**:
  - 現在の日本語エラー文面に対しては完全に動作しますが、将来的にサーバー側のメッセージ文面が変更された場合や、多言語対応（英語化等）が行われた場合に、クライアント側の自己修復判定が漏れる保守リスクがあります。
- **推奨対応**:
  - 将来的なリファクタリングにおいて、サーバー側レスポンスに `errorCode: 'FOLDER_NOT_FOUND' | 'FOLDER_TRASHED' | 'INVALID_FORMAT'` 等のエラーコードを含め、クライアント側ではコード値で分岐する設計とすることを推奨します。
